# معماری دیتابیس Streak OS v11 — «Delta Core»

این سند معماری لایه‌ی داده‌ی نسخه ۱۱ را توضیح می‌دهد: چگونه داده‌ها **به‌صورت دلتا** (فقط تغییرات) ذخیره می‌شوند، چگونه سینک گیت‌هاب با رشد دیتابیس مشکل پیدا نمی‌کند، و مسیر مهاجرت آینده به **PostgreSQL** چگونه باز گذاشته شده است.

---

## ۱. نمای کلی

```
┌────────────────────────────────────────────────────────────────────┐
│  UI / منطق برنامه (state در حافظه — بدون تغییر نسبت به نسخه‌های قبل) │
└──────────────────────────────┬─────────────────────────────────────┘
                               │ save()
                               ▼
                  ┌────────────────────────────┐
                  │  Delta Engine (dbDiffStates)│  diff نسبت به آخرین
                  │  before = __dbLastPersisted │  وضعیت ذخیره‌شده
                  └───────────┬────────────────┘
                              │  ops[] فقط برای رکوردهای تغییرکرده
              ┌───────────────┼────────────────────────────┐
              ▼               ▼                            ▼
   ┌────────────────┐  ┌──────────────────┐  ┌──────────────────────────┐
   │ جدول‌های دامنه  │  │ change_log       │  │ JSON-mirror اختیاری       │
   │ (IndexedDB      │  │ (ژورنال دلتا =    │  │ (فایل JSON برای همکاری/   │
   │  به‌ازای هر جدول)│  │ صف آپلود سینک)   │  │ بکاپ خارجی — بدون تغییر)  │
   └────────────────┘  └────────┬─────────┘  └──────────────────────────┘
                                │
                               ▼
                  ┌────────────────────────────┐
                  │ GitHub Delta Sync           │
                  │ manifest + delta files      │
                  │ + snapshots (Git Data API)  │
                  └────────────────────────────┘
```

**اصل طلایی v11:** هیچ عملیات معمولی «ذخیره»، کل دیتابیس را سریالایز یا بازنویسی نمی‌کند. فقط رکوردهای تغییرکرده نوشته می‌شوند و همان تغییرات به‌صورت عملیات (op) به ژورنال اضافه می‌شوند.

---

## ۲. مدل داده — نگاشت IndexedDB ↔ SQL

اسکمای مرجع: [`db/schema.sql`](schema.sql) (SQLite) و [`db/schema.postgres.sql`](schema.postgres.sql) (PostgreSQL).

| جدول SQL | Object Store در IndexedDB | نقش |
|---|---|---|
| `meta` | `t_meta` | نگهداری نسخه اسکیما، فلگ مهاجرت، salt رمزنگاری |
| `activities` | `t_activities` (keyPath: `id`) | فعالیت‌ها — یک رکورد به‌ازای هر فعالیت |
| `entries` | `t_entries` (اینکس: activityId, date) | ثبت‌های روزانه |
| `measurement_types` | `t_measurement_types` | کاتالوگ واحدها |
| `settings` | `t_settings` (کلید `global`) | پیش‌فرض‌های برنامه |
| `presets` | `t_presets` (keyPath: `name`) | پریست‌های تنظیمات |
| `change_history` | `t_change_history` | تاریخچه تغییرات UI (append-only) |
| `view_settings` | `t_view_settings` | تنظیمات UI **per-device** (سینک نمی‌شود) |
| `change_log` | `t_journal` (seq خودافزا) | **ژورنال دلتا** — قلب سیستم |
| `sync_state` | `t_sync_state` | نشانگر (cursor) دریافت از هر دستگاه |
| `tombstones` | `t_tombstones` | نشانگر حذف برای داوری LWW |

ستون‌های کلیدی جداول دامنه به‌صورت صریح و قابل‌ایندکس نگه داشته می‌شوند و `data_json` کل رکورد را بدون افت اطلاعات حفظ می‌کند (در PostgreSQL: `JSONB`).

## ۳. موتور دلتا

هر `save()`:

1. **Diff**: `dbDiffStates(before, after)` وضعیت فعلی را با آخرین وضعیت ذخیره‌شده مقایسه می‌کند (مقایسه canonical با مرتب‌سازی کلیدها) و فقط برای رکوردهای جدید/تغییرکرده/حذف‌شده op تولید می‌کند:
   - `entity ∈ {activity, entry, measurementType, preset, settings, history, meta}`
   - `op ∈ {upsert, delete, append}`
   - رکوردهای تغییرکرده یک `updatedAt` تازه می‌گیرند (استمپ داوری LWW).
2. **نوشتن اتمی**: تمام رکوردهای تغییرکرده در **یک تراکنش** IndexedDB در جدول‌های دامنه نوشته/حذف می‌شوند. برای حذف‌ها، tombstone هم ثبت می‌شود.
3. **ژورنال**: همان ops به `change_log` (t_journal) با `seq` یکنواخت صعودی append می‌شوند و `synced=0` می‌گیرند. این ژورنال همان **صف ارسال سینک** است.
4. **بازنویسی صفر**: تغییرات صرفاً UI (مثل عرض ستون‌ها یا اسکرول) فقط در `t_view_settings` می‌نویسند و **هیچ op‌ای** تولید نمی‌کنند — برخلاف v10 که کل دیتابیس را بازنویسی می‌کرد.

**چک‌پوینت/هرس:** عملیات‌های `synced=1` نگه‌داشته‌شده به ۵۰ مورد محدود می‌شوند (`dbJournalPrune`) و tombstoneها بالای ۴۰۰۰ مورد هرس می‌شوند. حجم محلی همیشه متناسب با داده‌ی واقعی است.

**رمزنگاری:** اگر گاوم رمزنگاری‌شده باشد، هر رکورد جداگانه با AES-GCM (کلید مشتق‌شده PBKDF2/310k) بسته‌بندی می‌شود — `recPack/recUnpack` شفاف برای بقیه سیستم. تغییر رمز = `dbRekey` روی همه‌ی storeها.

## ۴. سینک گیت‌هاب — مخزن دلتا (append-only)

به‌جای «یک فایل JSON بزرگ» که هر بار بازنویسی می‌شد، در مخزن داده‌ی شما این ساختار ساخته می‌شود:

```
streak-db/
├── manifest.json                          ← کوچک؛ تنها فایلی که بازنویسی می‌شود
├── deltas/<deviceId>/<from>-<to>.json     ← بسته‌های عملیات؛ فقط append می‌شوند
└── snapshots/<deviceId>/snap-<seq>.json   ← عکس کامل وضعیت؛ هر ~۸۰۰ عملیات یک‌بار
backups/                                    ← پشتیبان‌های دستی/تعارض (مثل قبل)
```

- **هر سینک = یک کامیت اتمی**: `POST /git/blobs` → `POST /git/trees` → `POST /git/commits` → `PATCH /git/refs` (Git Data API). فایل‌های داده‌ی بزرگ از محدودیت ۱ مگابایت Contents API عبور می‌کنند (Blob API تا ۱۰۰MB).
- **رشد تاریخچه‌ی گیت متناسب با تغییرات است، نه حجم دیتابیس** — چون بسته‌های دلتا هرگز بازنویسی نمی‌شوند و مانيفست چند کیلوبایت است.
- **Pull**: خواندن `manifest.json` (کوچک) → مقایسه‌ی cursor هر دستگاه → فقط فایل‌های دلتای جدید با Blob API گرفته و با داوری **LWW در سطح رکورد** اعمال می‌شوند.
- **Snapshot**: هر ۸۰۰ عملیات (یا هنگام import/rebase) یک snapshot کامل منتشر می‌شود و دستگاه‌های جدید می‌توانند مستقیماً از آن شروع کنند.
- **GC**: بسته‌ی دلتایی که توسط snapshotِ جدیدتر همان دستگاه پوشش داده شود **و** همه‌ی دستگاه‌های فعال (آخرین فعالیت < ۹۰ روز) آن را ack کرده باشند، در همان کامیت حذف می‌شود → پوشه‌ی داده بدون انباشت بی‌رویه می‌ماند.
- **تعارض هم‌زمانی push**: اگر ref بین blob و commit جابه‌جا شده باشد (409/422)، مانيفست دوباره خوانده و push تا ۴ بار بازسازی می‌شود.
- **Rebase (Overwrite cloud)**: snapshot با `epoch+1` منتشر می‌شود؛ دستگاه‌های دیگر در اولین pull، اختلاف epoch را می‌بینند، از وضعیت محلی پشتیبان می‌گیرند و روی snapshot جدید rebase می‌کنند.
- **مهاجرت از v10**: اگر `manifest.json` نبود ولی فایل قدیمی `streak-os-data.json` موجود باشد، یک‌بار در `backups/` پشتیبان گرفته می‌شود، داده‌ی آن ادغام/اقدام می‌شود و baseline جدید ساخته می‌شود. دیتابیس محلی v10 هم در اولین باز شدن به‌صورت یک‌باره به storeهای نرمال منتقل می‌شود.

### چرا دیتابیس سنگین دیگر گیت‌هاب را اذیت نمی‌کند؟

| مشکل v10 | راه‌حل v11 |
|---|---|
| هر سینک، کل JSON بازنویسی می‌شد (رشد تاریخچه = حجم DB × تعداد سینک) | فقط فایل‌های دلتای کوچک جدید + مانيفست کامیت می‌شود |
| محدودیت ۱MB خواندن Contents API | دریافت از طریق Git Blobs API (تا ۱۰۰MB) |
| هر دستگاه باید کل فایل را برای merge می‌خواند | فقط deltaهای بعد از cursor خوانده می‌شوند |
| بدون هرس؛ پوشه‌ی داده بی‌رویه بزرگ می‌شد | snapshot دوره‌ای + GC خودکار بسته‌های پوشش‌داده‌شده |
| تعارض = بازنویسی کامل فایل | کامیت اتمی + retry با re-pull |

## ۵. داوری تعارض (LWW متقارن)

- قاعده: استمپ زمانی جدیدتر (`updatedAt` رکورد در op) برنده است؛ در تساوی دقیق، شناسه‌ی دستگاه با ترتیب لغوی بزرگ‌تر برنده است — این قاعده **متقارن** است، پس همه‌ی دستگاه‌ها به یک نتیجه می‌رسند.
- برای `upsert` مقابل `delete` از **tombstone** استفاده می‌شود تا رکورد حذف‌شده با op قدیمی زنده نشود.
- `changeHistory` به‌صورت union بر اساس id ادغام می‌شود (هیچ‌چیز گم نمی‌شود؛ تعارض محسوب نمی‌شود).
- `viewSettings` اصلاً سینک نمی‌شود (تنظیمات UI per-device است)؛ `presets` حالا per-item ادغام می‌شود.
- نسخه‌های بازنده همیشه قبل از بازنویسی در `backups/` پشتیبان‌گیری می‌شوند.

## ۶. مسیر مهاجرت به PostgreSQL

سه لایه از هم جدا شده‌اند تا مهاجرت بدون بازنویسی منطق برنامه ممکن باشد:

1. **اسکیما**: [`schema.postgres.sql`](schema.postgres.sql) ترجمه‌ی مستقیم [`schema.sql`](schema.sql) است (JSONB، IDENTITY، TIMESTAMPTZ). هیچ نوع خاص SQLite در ستون‌های کلیدی استفاده نشده است.
2. **داده**: خروجی «SQLite database» (دکمه‌ی 🧱 در تنظیمات) یک فایل واقعی `streak-os-*.sqlite` با همین اسکیماست که با هر ابزار ETL استاندارد (pgloader، اسکریپت copy، …) قابل انتقال به PostgreSQL است. `change_log` دقیقاً همان **CDC stream** است که برای بارگذاری اولیه و همگام‌سازی تدریجی استفاده می‌شود.
3. **کد**: تمام دسترسی‌های داده از توابع Delta Core (`dbPersistCurrent`, `dbApplyRemoteOps`, `dbJournal*`, `dbSyncCursor`, …) عبور می‌کنند — یعنی یک `PgAdapter` سمت سرور با همان API می‌تواند جای IndexedDB بنشیند بدون اینکه UI/منطق برنامه دست بخورد. پروتکل سینک (manifest/delta/snapshot) هم backend-agnostic است.

### گام‌های پیشنهادی مهاجرت (وقتی به سرور نیاز شد)

1. یک API کوچک (Node/Express یا هر فریم‌ورک) بسازید که همان ۵ عملیات را ارائه دهد: `pull(manifest)`, `push(batches)`, `pushSnapshot`, `ack`, `snapshotLatest`.
2. `schema.postgres.sql` را اجرا کنید و دیتای اولیه را از فایل SQLite/JSON منتقل کنید.
3. در اپ، `DeltaBackend` را با `PgBackend` (همین اینترفیس) عوض کنید — بقیه‌ی سیستم دست‌نخورده می‌ماند.
4. برای چند کاربر واقعی، ستون `user_id` به جداول اضافه و در manifest همان scope اعمال شود.

## ۸. عیب‌یابی

- در دیالوگ تنظیمات، بخش «Sync & status» لاگ کامل رویدادهای سینک را نشان می‌دهد.
- کنسول: `window.StreakSync.journal()` عملیات‌های در صف ارسال، و `window.StreakSync.cursors()` نشانگرهای دستگاه‌ها را برمی‌گرداند.
- اگر مخزن داده دستی حذف/خراب شد: «Overwrite cloud» یک baseline جدید منتشر می‌کند؛ «Adopt cloud» وضعیت ابر را می‌پذیرد. در هر دو حالت پشتیبان خودکار گرفته می‌شود.

## ۹. لایه‌ی مسیریابی ذخیره‌سازی و چندپایگاه‌داده‌ای (v11.1)

### ۹.۱ Storage Router — رفع «Database is not ready» در حالت file://

مرورگرها (مثل Chrome) هنگام باز کردن مستقیم `index.html` از طریق `file://` اجازه‌ی دسترسی به IndexedDB را نمی‌دهند؛ در نتیجه تا قبل از v11.1 برنامه با خطای «Database is not ready» متوقف می‌شد. از v11.1 همه‌ی عملیات‌های ذخیره‌سازی از یک **مسیریاب** عبور می‌کنند:

```
stGet / stPut / stGetAll / dbBulkWrite / idbGet / idbPut
                    │
        STORE_MODE === 'idb' ?
           ├── بله → IndexedDB (پایگاه داده‌ی اختصاصی همان workspace)
           └── خیر → localStorage (پیشوند so-ws-<id>:)
```

- انتخاب موتور: یک probe سبک (`idbUsable()`) در بوت بررسی می‌کند IndexedDB واقعاً کار می‌کند یا نه؛ اگر نه، همان لحظه موتور localStorage فعال می‌شود.
- در localStorage هم هر رکورد یک کلید جدا دارد (`so-ws-<id>:t_entries:<uuid>`) — پس نوشتن همچنان **دلتای واقعی** است، نه بازنویسی یک بلاب بزرگ. ستون `seq` ژورنال با شمارنده‌ی per-workspace شبیه‌سازی می‌شود (معنای autoincrement حفظ شده).
- محدودیت حجم localStorage (~۵MB) با پیام خطای شفاف همراه است و خروجی JSON/SQLite همیشه به‌عنوان مسیر بایگانی در دسترس است.
- پارامتر diag: باز کردن صفحه با `?soStorage=ls` حتی اگر IndexedDB سالم باشد، مسیر localStorage را اجبار می‌کند (برای پشتیبانی و تست).

### ۹.۲ Database Registry — چند پایگاه داده با انتخابگر صفحه‌ی ورود

فهرست پایگاه‌های داده در `localStorage` (کلید `streak-os-registry-v1`) نگه‌داری می‌شود چون در همه‌ی origins — از جمله `file://` — در دسترس است:

```json
{"v":1,"activeId":"ws-…","workspaces":[
  {"id":"default","name":"Default","storage":"idb"},      ← دیتابیس قدیمی streak-os-db-v1 (به‌صورت خودکار پذیرفته می‌شود)
  {"id":"ws-…","name":"شغلم","storage":"idb"},            ← streak-os-db-ws-…
  {"id":"ws-…","name":"شخصی","storage":"ls"}              ← so-ws-ws-…:
]}
```

- **جداسازی کامل**: هر workspace یا یک پایگاه داده‌ی IndexedDB جداگانه دارد یا یک پیشوند جدا در localStorage؛ فعال‌سازی هر workspace همه‌ی حافظه‌های مرتبط با دلتا (`__dbLastPersisted`، شمارنده‌ی ژورنال، کلید رمزنگاری) را صفر می‌کند تا هیچ عملیاتی بین پایگاه‌ها نشت کند.
- **پذیرش خودکار**: اولین بوت پس از ارتقا، دیتابیس تک‌نفره‌ی قبلی را به‌عنوان workspace با شناسه‌ی `default` ثبت می‌کند — داده‌ها دست‌نخورده می‌مانند.
- **انتخاب فعال**: workspace فعالِ به‌یادسپاری‌شده → جدیدترینِ قابل‌استفاده → در نبود هیچ‌کدام، ساخت خودکار یک workspace تازه. یعنی باز کردن فایل هیچ‌گاه به بن‌بست «Database is not ready» نمی‌خورد.
- هر workspace اطلاعات خودش را در همان جدول‌های Delta Core (شامل `change_log` و `sync_state`) نگه می‌دارد؛ بنابراین سینک گیت‌هاب و مهاجرت PostgreSQL به‌ازای هر پایگاه داده مستقل کار می‌کند.
